# When Confidence Overrides Consensus: An Empirical Boundary Analysis of Scoring Signals

This repository contains the generation scripts, candidate ledgers, scoring outputs and analysis code
behind every table and figure in the manuscript.

Two populations are archived side by side:

- **Primary study** (top level): 600 questions × 3 provider-hosted configurations = 1,800
  model–question records, of which 209 contain competing answer classes. Collected with seven
  samples per question at temperature 1, plus a separate 0–100 self-confidence elicitation.
- **Expanded study** (`expanded/`): 2,400 questions × 2 small local generators = 4,800 records,
  of which 2,544 contain competing classes. This population carries the eight single signals and
  the three solver conjunctions compared in Table 4 and Table 7.

## Layout

```
data/            question-level rows, ledgers, compressed request/response archives
analysis/        offline replay, statistics and figure programs (no network, no keys)
protocols/       frozen specifications, development locks, parser mapping
tables/          fixed-policy counts, pool coverage, score-quality and parser results
figures/         the manuscript figures as PDF
figure_data/     numeric sources behind each figure (CSV)
documentation/   provenance notes, metric definitions, style manifest
expanded/        the 4,800-record population
  data/          question sets, task files, the 209-pool certificate ledger
  out/           generation outputs, per-signal scores, solver answers, result tables
  scripts/       generation, scoring and analysis programs for that population
```

## Quick start (primary study, fully offline)

```
python3 -m pip install -r analysis/requirements.txt
python3 analysis/run_all.py
```

`run_all.py` replays the frozen rows, recomputes the clustered statistics, parser diagnostics and
figures, and writes its outputs into `data/`, `figures/` and `figure_data/`. It makes no model or
network requests. Complete retained response exports are checked against body and request-identity
hashes, so the replay fails loudly if an archived payload has been altered.

## A note on model labels

The two DeepSeek judge arms and the two DeepSeek solver arms are one model in different modes:
DeepSeek-V4.1-Flash, served under the provider identifier `deepseek-flash` (snapshot
DeepSeek-V4.1-Flash-1017 when the runs were made). The provider exposes no separate identifier for
the thinking switch; it is selected by the request — `deepseek-chat` for the non-thinking arm and
`deepseek-reasoner` for the thinking arm. Every label in this package now names the model and the
mode (`DeepSeek judge (thinking)`, `DeepSeek solver (non-thinking)`, …), which is how the manuscript
refers to them. The archived console outputs were relabelled after the runs; their counts, intervals
and tests are unchanged.

The generator is the same model again: `expanded/scripts/gen_pipeline.py` calls
`deepseek-flash`, which the provider resolves to the same backend. Section 6.3 of the manuscript
states the consequence — 76 of the 209 primary pools are checked by a same-model cross-examination.

## Paths in the collection scripts

Every program resolves its data directory from its own location: `expanded/scripts/` opens
`expanded/data/` and `expanded/out/`, and `analysis/` resolves paths relative to the repository root,
so both run from a fresh checkout. Set the environment variable `EXP_BASE` to override the root of
the expanded-study tree (for example when the outputs live on a scratch volume).

## Environment

Python 3.11 or later with `analysis/requirements.txt` for the offline replay; the collection scripts
additionally used `requests`. Inference ran on llama.cpp `llama-server` (OpenAI-compatible endpoint)
for the local models, and on the providers' HTTP APIs at temperature 0 for judges and at temperature
1 for generation. No model weights or inference binaries are bundled. Model weights remain under
their upstream licences; see `LICENSES/`, `LICENSE_SCOPE.md` and `THIRD_PARTY_NOTICES.md`.
